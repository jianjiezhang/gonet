# 游戏服务器主程学习计划

面向：在 Linux 本机上，用闲暇时间锻炼操作系统排错、服务器组件与游戏服后端能力。  
假设节奏：每天 **60–90 分钟**，每周 **5–6 天**。  
预期：约 **12–18 个月** 后具备可独立扛游戏服后端的基础（主程不是速成，靠深度堆积）。

---

## 总原则

1. **本机就是实验室**：每个概念都要在这台 Linux 上跑一遍命令、看一遍输出、改一下配置再看变化。
2. **先会读现象，再学框架**：不会读 `ss` / `dmesg` / `journalctl`，上 K8s 也只是把问题藏进 YAML。
3. **语言为服务服务**：游戏服主程常见组合是 **Go（业务/网关/工具）+ C++（高性能循环/引擎侧）+ 少量 Java（若公司栈是 Java）**。先 Go，并行补 C++，Java 按需。
4. **每个周末做一个能演示的小东西**，否则知识不会变成手感。
5. **写故障笔记**：现象、命令、输出里哪一行说明了什么、根因、修复。这就是主程面试和线上值班的素材。
6. **环境要隔离**：破坏性实验优先用虚拟机快照，或至少用独立目录 / loop 设备，避免把日常系统搞到起不来。
7. **一次只注入一个主因**：磁盘满同时再搞坏 DNS，很难练出清晰因果。排错时不要对着制造故障的脚本看答案。

---

## 练习方法（如何捣鼓这台电脑）

四种互补练法：

1. **故障注入**：自己制造一类问题，然后不看脚本，只看现象排错。
2. **先观察、后解释**：正常时记下基线，出问题后对比。
3. **真实故障复盘**：论坛/自己踩坑，只给现象，列假设 → 验证 → 结论。
4. **结构化挑战**：限时给出根因和修复步骤。

每个场景写一张故障卡：

- 用户可见现象
- 可能的 3 个原因
- 实际执行的命令和输出要点
- 根因一句话
- 修复与如何避免再发生

真正拉开差距的能力：

- **先分层**：硬件/内核 → 资源 → 配置 → 应用，不要一上来重装。
- **一次只改一个变量**，改完立刻验证。
- **留下证据**：命令、时间、输出。
- **修复后做回归**：服务是否自动拉起、重启后是否还在。

不要用「重装系统」当排错手段。不要对非自己的机器做破坏性实验。

## 阶段 0（3–5 天）：把这台机器变成可练的服务器

目标：能 SSH 进自己、改配置不怕搞坏、日志找得到。

每天捣鼓：

- 终端、`tmux` 或 `screen`（断线任务还在）
- 普通用户 + `sudo`，不要整天 root 上网
- 装一套固定工具并记住它们干什么：  
  `htop`、`iotop`、`sysstat`（`iostat` / `pidstat`）、`strace`、`lsof`、`tcpdump`、`jq`、`curl`、`git`
- 学会：`man`、`--help`，每个命令先搞清 3 个最常用参数

本机实验：开 `sshd`，本机 `ssh 127.0.0.1`；有条件则做快照 / Timeshift，建立「敢改配置」的习惯。

## 阶段 1（4–6 周）：排错指令、读输出、看底层

这是第一个目标，也是主线。按子系统练，不要按命令字典背。

### 每天固定流程（15 分钟观察 + 45 分钟专题）

先在**正常状态**跑一遍体检，把输出存成文本作为基线：

```bash
uptime
free -h
df -h; df -i
systemctl --failed
ss -lntp
journalctl -p err -b --no-pager | tail
```

出问题后跑同一组，做对比。主程排错的本质就是 **diff 基线**。

排错时优先会用：

- **现在发生了什么**：`journalctl -xe`、`journalctl -u <服务> -b`、`dmesg -T`
- **资源**：`htop` / `btop`、`free -h`、`df -h`、`iostat -xz 1`
- **网络**：`ss -lntp`、`ip route`、`resolvectl status`
- **服务**：`systemctl --failed`、`systemctl status`

进阶再加 Prometheus + node_exporter、Netdata、Cockpit。大盘看趋势；根因仍在日志和配置里。

### 按子系统分关

| 关卡 | 典型现象 | 该练的工具 |
|------|----------|------------|
| 磁盘 / inode | 写文件失败、日志停更、apt 报错 | `df -h` / `df -i`、`du`、`lsof`、journal |
| 内存 / OOM | 进程突然没了、卡死 | `free`、`dmesg`、`journalctl -k`、`oom_score` |
| CPU / 负载 | 很卡但 CPU 不高，或 load 很高 | `uptime`、`vmstat`、`pidstat`、`iowait` |
| 进程 / 权限 | 服务起不来、Permission denied | `systemctl status`、`strace`、`namei -l` |
| systemd | 开机失败、依赖循环、超时 | `systemctl`、`journalctl -b`、`systemd-analyze` |
| 网络 | ping 通但解析失败、端口没监听 | `ip`、`ss`、`resolvectl`、`nft` / `iptables` |
| 存储 / IO | 卡顿、只读文件系统 | `dmesg`、`smartctl`、`mount`、`fsck`（谨慎） |
| 包与依赖 | 半升级、依赖断裂 | `apt`、`dpkg -l`、`/var/log/apt` |
| 用户 / 认证 | 登不上、sudo 失败 | pam、sshd 日志、`getent` |
| 启动 / 内核 | 进不了系统（高级） | GRUB、recovery、串口日志 |

先把前 6 关练到「闭着眼睛知道先看哪几个命令」，再碰内核和启动。

适合在自己机器上模拟的运维事故（一次一个）：

- 根分区或 `/var` 写满；inode 耗尽（大量小文件）——不要灌满到系统起不来，用单独目录或小 loop 设备
- 某个服务的日志没轮转
- systemd 单元 `After=` / `Requires=` 写错、环境变量路径错
- 监听地址绑到 `127.0.0.1`，外网连不上
- DNS 配错、`/etc/hosts` 误改、默认路由丢了
- 文件权限 / 属主被改，服务用户读不了配置
- 时区 / 时间不同步导致证书或 cron 异常
- 磁盘只读、挂载点被占、swap 没挂上
- apt 源不可达、dpkg 中断在 half-configured

### 第 1 周：进程与服务（systemd）

| 命令 | 要读懂的 |
|------|----------|
| `ps aux` / `ps -ef` | USER、PID、%CPU、%MEM、STAT（R/S/D/Z）、COMMAND |
| `top` / `htop` | load 三个数字、%wa（IO 等待）、谁在吃 CPU |
| `systemctl status` / `cat` | Active、Main PID、cgroup、最近日志 |
| `journalctl -u xxx -b` | 时间、优先级、哪一行是原因哪一行是结果 |

本机实验：写一个会崩溃的小服务（Go 或 bash），用 systemd 托管，故意让它失败，练 `status` + `journalctl` 找到原因。

### 第 2 周：内存与 OOM

读懂：`free -h` 的 available vs free；`/proc/<pid>/status` 的 VmRSS；`dmesg` 里 `Out of memory`。  
本机实验：限制一个进程的内存（cgroup 或 systemd 的 `MemoryMax=`），看它被杀时内核怎么说。

### 第 3 周：磁盘、inode、只读、IO 等待

读懂：`df -h` vs `df -i`；`iostat -xz 1` 的 `%util`、`await`；`dmesg` 的 I/O error、Remounting filesystem read-only。  
本机实验：对比「空间满」和「inode 满」。

### 第 4 周：网络（游戏服最重要）

| 命令 | 要读懂的 |
|------|----------|
| `ip addr` / `ip route` | 地址、默认路由 |
| `ss -lntp` / `ss -antp` | LISTEN、ESTAB、TIME-WAIT、哪个进程占端口 |
| `resolvectl` / `dig` | DNS 是否正常 |
| `ping` / `curl -v` | ICMP 通不等于业务通 |
| `tcpdump -i any port 8080` | SYN、握手、有没有包进来 |

本机实验：写一个 TCP 小服务（Go），分别制造「没监听」「只绑 127.0.0.1」「防火墙丢掉」「进程阻塞不 accept」，用 `ss` / `tcpdump` 区分这四种。

### 第 5–6 周：系统调用与底层展示

- `strace -p PID`：进程卡在 `futex`、`read`、`accept`、`epoll_wait` 分别意味着什么
- `lsof -p PID`：打开了哪些端口、文件、socket
- `/proc/<pid>/{fd,stack,limits,io,net}`：不装额外工具也能看
- `perf top` 或 Go `pprof`：CPU 热函数（入门即可）

本机实验：写一个「看起来卡住」的服务器（死锁 / 阻塞在磁盘 / 等锁），只用 `strace` + `ss` 判断卡在哪一层。

### 阶段 1 毕业标准

别人只说「登不上 / 很卡 / 连不上 / 服务起不来」，能在约 20 分钟内判断是 **进程死了、没监听、资源耗尽、DNS、权限、还是应用逻辑**，并能指出是哪一条命令的哪一列得出结论。

## 阶段 2（3–4 周）：计算机网络 + 游戏服连接模型

每天学一点，本机立刻写：

- TCP 握手、TIME_WAIT、keepalive、Nagle、缓冲
- UDP：丢包、乱序；游戏同步为什么常用 UDP + 自建可靠
- `epoll` / `io_uring` 要解决什么问题（C10K：不是「线程不够」而是事件模型）
- 延迟构成：序列化、排队、DB、锁、GC、系统调用

本机小项目（必须做）：

- echo TCP 服务器（Go）：单线程事件循环 vs goroutine per conn，用 `ss` 看连接数
- 用 `wrk` / `hey` 压一下，同时开 `htop`、`ss -s`，解释 load 和连接状态
- 再写一个 UDP 回包，用 `tcpdump` 看包

读物：Stevens 当词典查；先把 Beej’s Guide to Network Programming + 自己抓包练熟。

## 阶段 3（8–12 周，可与阶段 2 部分重叠）：语言

### Go（主攻）

游戏服网关 / 大厅 / 匹配 / 工具链最常见。  
节奏：每天约 40 分钟语法 / 标准库 + 20 分钟接到「像服务器的东西」上。

顺序：

1. goroutine、channel、`context`、错误处理
2. `net`、`net/http`、JSON
3. 并发安全：`mutex`、不要在热路径乱 `go`
4. `pprof`、`trace`、竞态检测 `go test -race`
5. 一个最小房间服：登录 → 进房 → 广播聊天（内存即可）

### C++（高性能与引擎侧）

每周 2–3 晚即可，不要和 Go 抢同一天的深度。  
顺序：对象模型、RAII、移动语义、多线程、`asio` 或自己写 epoll 小 demo。  
目标：看懂帧循环、对象池、无锁队列在说什么，能和引擎同事对齐。

### Java

若明确要去 Java 栈工作室再加：JVM、GC 日志、Netty。否则先标记为「能读代码」。

## 阶段 4（6–8 周）：服务器常用组件（先单机，再谈分布式）

原则：每个组件都在本机用 Docker 或原生安装跑起来，然后故意弄坏它，用阶段 1 的命令看。

推荐顺序（贴近游戏服，也适合一台电脑）：

| 顺序 | 组件 | 亲手要做的 | 和游戏服的关系 |
|------|------|------------|----------------|
| 1 | Redis | 安装、`redis-cli`、string/hash/zset、过期、AOF/RDB | 会话、排行榜、房间、锁、缓存 |
| 2 | PostgreSQL 或 MySQL | 表、索引、慢查询、连接数 | 账号、订单、持久数据 |
| 3 | RPC | 先 gRPC + protobuf；Thrift 作为对照读一遍协议差异 | 大厅 ↔ 场景 ↔ 战斗 |
| 4 | 消息队列 | 先 NSQ 或 NATS（轻）；Kafka / Pulsar 放到能理解分区 / 积压之后 | 邮件、日志、跨服事件、解耦 |
| 5 | Nginx | 反代、限流、WebSocket 升级 | 网关前、管理后台 |

Pulsar 能力很强，但运维和心智比 NSQ/NATS 重。作为主程：先把「队列积压、重复消费、分区、至少一次 / 恰好一次」搞懂，再上 Pulsar。

每个组件的排错作业（把目标 1 和目标 2 焊在一起）：

- Redis 打满内存 / 持久化把磁盘写满 → `INFO`、日志、`df`
- 数据库连接打满 → `ss`、`SHOW PROCESSLIST`、应用侧报错
- 队列消费者挂了 → 积压数字、进程是否还在、`journalctl`

## 阶段 5（6–8 周）：分布式与 K8s

不要一上来就搭多机集群。本机用 **k3s** 或 **kind** 足够。

顺序：

1. 进程间通信：本机多个二进制 + Redis + RPC，先形成「逻辑分布式」
2. 容器：Dockerfile 打包 Go 房间服
3. k8s 最小集：Pod、Service、Deployment、ConfigMap、探针、资源限制
4. 用 `kubectl logs` / `exec` / `describe` 排错——和 `journalctl` / `ss` 是同一套思维

主程要懂的 K8s：滚动发布、失败回滚、CPU/内存 limit 导致 throttle、探针杀进程、服务发现。不是先考证书。

## 阶段 6（贯穿后 6 个月）：假游戏服主项目

闲暇时间以它为圆心。

最小架构（全在本机）：

```
客户端（可先用 curl / WebSocket 脚本）
    → Gate（Go，TCP/WS）
        → 大厅（登录、匹配）
        → 房间（帧或状态同步简化版）
        → Redis（会话 / 房间）
        → DB（账号）
        → 队列（异步邮件 / 日志）
```

版本迭代（每 2–3 周一个）：

- v0：单进程能聊天
- v1：Gate + 房间拆开，RPC
- v2：Redis 会话，进程重启玩家还能回来
- v3：故意杀掉房间进程，看匹配 / 重连
- v4：接入 Prometheus 指标（在线、延迟、队列积压）+ 用 Linux 命令验证数字是否骗人
- v5：打成容器，k3s 里跑两副本

主程能力在这里体现：协议、状态、故障、观测、发布，而不是「用过某某中间件」。

**看系统：** `htop`、`iotop`、`sysstat`、`strace`、`lsof`、`tcpdump`；后期 `bpftrace`

**压测：** `hey`、`wrk`、自己写的机器人

## 明确不做什么

- 不要一开始就搭 Pulsar 多机、全套服务网格、自研引擎
- 不要用生产数据、不要对非你的机器做破坏性实验
- 不要用重装系统当排错手段
- Java 全家桶：除非目标公司就是那套，否则后置
- 不要去练未授权入侵、提权利用——和操作系统排错、游戏服主程是两条线

## 12 周后应能当面讲清楚的 10 件事

1. load average 高，如何判断是 CPU、IO 还是过多可运行线程
2. 端口占用、只监听 localhost、连接打满的差别
3. 进程 STAT 为 D 意味着什么
4. OOM 时该看内核日志还是应用日志
5. Redis 缓存击穿和内存打满时怎么确认
6. TCP TIME_WAIT 大量出现时担不担心、为什么
7. goroutine 泄漏在 `pprof` 里长什么样
8. RPC 超时是网络、序列化还是下游慢
9. 队列积压时先看生产者还是消费者
10. 游戏服掉线：是网关、房间崩溃，还是 Redis 会话丢了

讲得清这 10 件，第一个目标（排错与读底层）就算达标；后面的中间件只是同一套眼睛换了对象。
