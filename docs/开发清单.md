# 反向贪吃蛇开发清单

本文是后续开发顺序，不是当前已落地行为。当前行为以 `docs/architecture.md` 为准。

`clientgame` 在服务端这条链路能打完整场之前不改。

## 已定顺序

1. 一个进程里做完玩家、好友、聊天、公会。
2. 再做空房间（开房、进房、空结算），玩法先不写。
3. 社交跨服先于战斗跨服。
4. 玩法定下来之后再做帧同步和少量服务器校验。
5. 最后改 `clientgame` 接入服务端。

## 全程接法

- 玩家服务继续用现有 `role`。连接在 `watchdog` 登录之后只交给这个 `role`，别名就是 `roleid`。
- 好友是一个具名服务。公会是 `guildmgr` 加「一个公会一个 actor」。聊天还没做。
- 客户端协议进 `role` 的 `ActorMessage.go`，再由 `role` 转给这三个服务。
- 关系数据进现有 MySQL（`store`，不是新 actor）。谁在线由本节点 `onlinemgr` 记在内存里。最近一次登录、下线时间在 `role` 表，unix 秒。
- 一场战斗一个 actor。人数、是人还是机器人，都由这一场的参数决定。
- 玩法不放进 `gonet/`。
- 服务别名按以后能 `harbor.Publish` 来起，调用仍走别名。

## 1. 玩家在线

已落地：`onlinemgr` 维护本节点在线名单。`role` 接上连接时 `Send` 上线，`Term` 时 `Send` 下线。`role.lastlogintime` / `role.lastlogouttime` 为 unix 秒。查询走 `online.query`。广播走 `online.broadcast.all` 和 `online.broadcast.some`，role 收到 `online.push` 后写给客户端。

做完的标志：两个客户端先后登录、下线，`online.query` 跟着变；广播只到达当时在线的人。

## 2. 好友

已落地：双向申请，同意后成为好友。申请留在库里，对方不在线也在。人数上限 50。没有黑名单。

- `friend` 一个 actor，内存里放全服好友边和未处理申请，变更异步写入 `friend` / `friend_request`。
- `role` 不存好友列表。客户端命令由 `role` 转给 `friend`，列表再补名字、等级，并用 `online.query.batch` 补是否在线。
- 对方在线时，`friend` 把 `friendnotify` 推到对方的 `role`。

做完的标志：A、B 两个 `roleid` 走 `cmd/client` 完成申请和同意，一方下线，另一方 `friendlist` 里看到离线。

## 3. 聊天

开工前先定：第一期要哪些频道（私聊、世界；公会频道先不做），以及离线后历史留不留、留多久。

然后做：

- `.chat` 一个 actor。
- 在线消息：`.chat` 按 `roleid` 找到对方 `role`，由对方 `role` 写出连接。
- 要留历史的话，正文进 MySQL；不留就只转在线玩家。
- `role` 增加发送和收消息的客户端命令。

做完的标志：两个在线玩家能按已定频道互发一条消息，不经过房间。

## 4. 公会

已落地。名字用 guild，不用 alliance。

- `guildmgr` 一个 actor，别名 `.guildmgr_<nodeid>`。管创建、公会名、玩家属于哪个公会，并拉起公会 actor。
- 一个公会一个 actor，别名 `guild/<id>`。管这一公会的公告、成员、申请。
- 一个人只能在一个公会。职位目前只有会长和成员。任何还没入会的玩家可以创建。没有人数上限。
- 会长不能退出，只能解散。解散后公会删除，成员不再属于任何公会。申请留在库里，对方不在线也在。
- 表：`guild`、`guild_member`（`roleid` 主键）、`guild_apply`。名字和在线不入库，列表时由 role 去补。
- 客户端命令进 role，再转给 guildmgr 或对应的公会 actor。`guilds` / `guildid` / `guildname` 查目录：全部、按 id、按名字。条目含公告、会长、人数；会长名字和在线由 role 补。

做完的标志：两人组成一个公会，都能拉到成员列表。公会聊天还没做。

## 5. 空房间

玩法仍不写。只做开房、进房、空结算。

- `.match` 一个 actor，负责建房间。
- 每一场 `NewService` 一个场景 actor，别名用这场的房间 id。人数、模式 id 放在创建参数里。
- 玩家操作路径仍是：客户端 → 自己的 `role` → 场景 actor。场景 actor 不拿 `net.Conn`。
- 场景里只记「谁在座」。结算消息发回各 `role`，然后这个场景 `Exit`。
- 机器人此阶段不生成。

做完的标志：`cmd/client` 用不同人数参数开两场，每场是不同的 actor，结算后 actor 消失，`role` 还在。

## 6. 社交跨服

单进程社交闭环通过之后再拆进程。用现有 `harbor` / `harbormgr`。

- 一个节点专门放 `.friend`、`.chat`、`.guildmgr`。公会 actor 别名是 `guild/<id>`。
- 其他节点只跑 `watchdog` + `role`。`role` 仍按别名 `Call` 这三个服务。
- 每个节点一个 `onlinemgr`，只记连在本节点的玩家。跨节点怎么查在线，做社交跨服时再定。
- 战斗节点此阶段不加入。

做完的标志：两个进程上的玩家能加好友、私聊、进同一个公会。

## 7. 帧同步

这一段等第一套玩法定下来再生效：猎人追逐、猎场信使，或新模式；以及这一场是「一人加机器人」还是「全是玩家」。

权威方式已定：帧同步，加少量服务器校验。

- 场景 actor 按帧收各座位的操作，按帧号广播给这场里的每个 `role`。
- 机器人的操作由这个场景 actor 在同一 mailbox 里生成，不再为机器人开 actor。
- 服务器只做少量检查：帧号连续、操作属于本座位、明显非法的输入丢掉。蛇的走位仍由各客户端按同一帧输入自己算。
- 结算条件由这套玩法给出，场景 actor 广播结算后 `Exit`。

做完的标志：用测试客户端打完一整场，两边收到的帧序列一致，结算只发生一次。

## 8. 战斗跨服

- 场景 actor 可以开在单独的节点上，`Publish` 房间别名。
- 玩家节点上的 `role` 把操作转到那个房间别名，状态帧再回到本节点 `role` 写出。
- 连接仍留在玩家自己的节点。

做完的标志：两个玩家节点的人进同一个远程房间，打完第 7 段那套玩法。

## 9. 接入 clientgame

服务端第 7 段能打完整场之后再改。若要跨服对局，则等第 8 段完成。

登录页由游戏进程提供（`web_port`，中心配置是 `http://127.0.0.1:5173/`）。登录走 `/api/session`：WebSocket 把玩家帧转到本机玩家口，连接保持，游戏进程每 5 秒往这条连接写 heartbeat。登录后是主页，个人资料里已接 `roleinfo` 和 `setlevel`，任务页已接 `missionlist` 和 `missionfinish`，玩法入口进原来的单机选关。对局仍在浏览器里算。好友、公会、聊天、房间、帧同步还没接到这个页面。

## 开工前仍要拍板

第 1 段可以先做。第 2、3、4 段开始前补上：

- 好友：同意还是单方面关注、人数上限、要不要黑名单、离线申请留不留。
- 聊天：第一期频道（私聊、世界）、离线历史留不留、留多久。
